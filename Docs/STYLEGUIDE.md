# Style Guide

## 목적

이 문서는 AI 에이전트가 코드를 작성할 때 따라야 할 Unreal C++, Blueprint, 에셋, 주석 규칙의 기준입니다.

## 공통 원칙

- 처음 보는 사람도 읽을 수 있도록 과도한 난이도의 패턴을 피합니다.
- 역할과 상태 소유권이 이름과 파일 배치에서 드러나게 작성합니다.
- 지금 task에 필요한 동작만 만들고, 미래 시나리오를 예상한 추상화는 기본적으로 추가하지 않습니다.

## 이름 규칙

- 클래스, 함수, 파일, 자산 이름은 모두 역할이 드러나게 작성합니다.
- 현재 프로젝트에 이미 확정된 네이밍 규칙이 있으면 그 규칙을 우선합니다.
- 실제 이름을 알 수 없는 기존 자산이나 기능은 추측해서 존재하는 것처럼 적지 않습니다.

### Aeterna 시나리오 이름

- 시나리오 ID는 `S01`부터 `S03`까지 두 자리 숫자로 표기합니다. 출시 기준 밤은 3개이며, 밤 3개 완성 전에는 ID를 늘리지 않습니다 (GDD §11-2).
- 특정 밤에서만 사용하는 자산은 Unreal 접두어 뒤에 시나리오 ID를 붙여 소유 범위를 드러냅니다. 예: `BP_S02_FossilShadow`, `DT_S03_LightSchedule`.
- 여러 밤이 공유하는 자산에는 특정 시나리오 ID를 붙이지 않습니다.
- `ScenarioManager`, `GameClock`, `NotebookRules`, `FailureSystem`은 책임 개념명입니다. 실제 클래스명은 선택한 Unreal 타입의 접두어 규칙을 따릅니다.

### Unreal 자산 이름

- Character와 일반 Actor Blueprint는 `BP_AssetName` 접두어를 우선 사용합니다.
- UI는 `WBP_AssetName`, 애니메이션 Blueprint는 `ABP_AssetName`을 우선 사용합니다.
- 맵은 퍼시스턴트 레벨 `Museum_Persistent`, 서브레벨 `Sub_MapName` 형식을 사용합니다 (`Sub_GrandHall`, `Sub_UtilityRoom` 등). **`L_` 접두어는 사용하지 않습니다.**
- 데이터 자산이 실제 task에서 필요하다고 승인된 경우 `DA_AssetName`, 데이터 테이블은 `DT_AssetName` 형식을 우선 사용합니다.
- 머티리얼은 `M_AssetName`, 머티리얼 인스턴스는 `MI_AssetName`을 사용합니다.
- 태그와 ID는 영문 스네이크/파스칼로 일관되게 작성합니다. 예: `Patrol_A`, `Light_Emergency_Red_01`.

전체 네이밍 표는 `AGENTS.md` §4-2가 기준이며, 이 문서와 충돌하면 `AGENTS.md`를 따릅니다.

### C++ 파일 이름

- C++ 파일 이름은 클래스 이름과 같은 기본 이름을 사용하고 헤더와 구현 파일을 같은 기본 이름의 `.h`, `.cpp` 쌍으로 유지합니다.
- Unreal 클래스 접두어는 클래스 선언에 따르고, 파일 이름은 접두어를 제외한 실제 클래스 이름 기준으로 맞춥니다.

예시:

- `AAeternaCharacter` → `AeternaCharacter.h`, `AeternaCharacter.cpp`
- `UScenarioStateComponent` → `ScenarioStateComponent.h`, `ScenarioStateComponent.cpp`

## Unreal C++ 규칙

- Actor, Component, Subsystem, UI처럼 책임 단위가 보이게 코드를 구성합니다.
- 현재 시나리오 전용 상태와 전체 진행 유지 상태를 같은 클래스에 편의상 누적하지 않습니다.
- 개별 이상 현상이나 상호작용 Actor가 전체 시나리오 시작·종료·시간 복구를 직접 제어하지 않게 합니다.
- “S02 이후에도 쓸 것 같다”는 이유만으로 인터페이스, 베이스 클래스, 범용 데이터 구조를 미리 만들지 않습니다.
- 규칙, 시각 이벤트, 조명 ID, 실패 조건, 수첩·로그 텍스트를 C++이나 Blueprint에 **하드코딩하지 않습니다.** DataTable(CSV)과 String Table을 경유합니다 (`AGENTS.md` §3-6, §4-3).
- 조작 입력은 WASD·Shift·Tab·E·F **5종으로 고정**입니다. 새 입력 액션을 추가하는 코드를 작성하지 않습니다 (`AGENTS.md` §3-1).

## Blueprint 규칙

- Blueprint는 상태 흐름과 이벤트 연결이 읽히게 구성합니다.
- 하나의 Blueprint에 관련 없는 여러 시스템을 몰아넣지 않습니다.
- 현재 task 범위에서 필요한 입력, 상태 변화, 사용자 반응만 노출합니다.
- 시나리오 전용 Blueprint는 재시작 또는 종료 시 어떤 상태가 초기화되는지 추적할 수 있게 구성합니다.
- 수첩 규칙의 승인된 문구와 순서를 Blueprint 편의를 위해 임의로 요약하거나 재작성하지 않습니다.

## Unreal Editor 작업 규칙

- Unreal Editor에서 일반적으로 생성·설정하는 에셋과 설정은 사용자가 명시적으로 요청하지 않는 한 코드로 대체 생성하지 않습니다.
- 해당 자산이 필요하면 사람이 에디터에서 직접 만드는 전제로 작업합니다.
- 맵이나 다른 자산에 배치해 사용하는 대상은 사용자의 별도 요청이 없으면 C++ 클래스를 바로 배치하기보다 Blueprint 등 에디터 자산으로 만들어 사용합니다.
- 에디터에서 선택·배치·연결하는 대상은 코드에서 구체 대상으로 자동 확정하지 않고 기본적으로 에디터에서 설정 가능하게 둡니다.

## 에셋 규칙

- 임시 검증 에셋과 최종 에셋은 구분 가능하게 관리합니다.
- 모델, 애니메이션, UI, 오디오 자산은 현재 task에서 필요한 상태 구분과 사용자 인지를 지원해야 합니다.
- 시나리오 전용 특수 오브젝트는 다른 시나리오에 상태가 남지 않도록 소유 범위를 분명히 합니다.
- 구체 시나리오 기획이 승인되기 전에는 제목, 규칙 문구, 이상 현상 명칭을 최종 에셋명으로 확정하지 않습니다.

## 주석 규칙

- 초보자 기준으로 이해를 돕는 주석은 허용합니다.
- 주석은 기본적으로 한글로 작성합니다.
- 왜 이런 분기나 상태 처리가 필요한지처럼 코드만으로 바로 드러나지 않는 맥락을 우선 기록합니다.
- 함수에는 어떤 기능을 하는 함수인지 주석을 작성합니다.
- 실패 롤백과 유지 상태 경계처럼 잘못 수정하면 진행 데이터가 오염되는 부분은 이유를 주석으로 남깁니다.

## 금지 또는 제한 규칙

- 플러그인, 모듈, 시스템 도입 같은 task 범위 밖 작업은 `Docs/WORKFLOW.md`의 `진행 제약`을 따릅니다.
- 비밀값 취급 규칙은 `Docs/WORKFLOW.md`의 `진행 제약`을 따릅니다.
- “나중에 쓸 수도 있다”는 이유만으로 미사용 상태, 더미 데이터 구조, 가짜 설정 항목을 추가하지 않습니다.
- 승인된 Aeterna 기획 기준과 다른 흐름을 임시 편의 기능으로 숨겨 넣지 않습니다.

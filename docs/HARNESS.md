# Harness

## 목적

이 문서는 세션 시작 시 AI 에이전트에게 하네스 엔지니어링 개념을 알리고, 에이전트가 규칙을 벗어났을 때 어떤 문서에 무엇을 추가하거나 수정해야 하는지 판단하는 기준입니다.

## 하네스 엔지니어링 기준

이 저장소에서 하네스 엔지니어링은 모델 성능 자체보다, AI 에이전트가 안정적으로 작업하도록 만드는 작업 환경 설계를 뜻합니다.

- 에이전트는 구현뿐 아니라 현재 작업 흐름이 안전하고 반복 가능하게 유지되는지도 함께 확인합니다.
- 같은 의미의 규칙은 담당 문서에 한 번만 두고, 다른 문서에서는 해당 기준을 가리킵니다.
- 반복해서 무시되는 산문 규칙은 단순히 더 강한 문장으로 바꾸지 않고, 승인 양식·체크박스·검증 항목처럼 실제 작업 시점에 작동하는 형태로 승격합니다.
- `AGENTS.md`의 `Aeterna 기획 기준`은 프로젝트 설계의 단일 기준점입니다. 변경은 일반 구현 수정과 구분해 승인과 출처 기록을 남깁니다.

## 하네스 이탈 대응

- 하네스 이탈은 에이전트가 스스로 감지하거나 사용자가 지적하는 두 가지 경우로 발생합니다.
- 사용자가 하네스 이탈을 지적하면 즉시 반박하거나 해명하지 않고 사실부터 확인합니다. 지적이 사실이면 어떤 절차가 지켜지지 않았는지 인정한 뒤 아래 절차를 진행하고, 사실이 아니면 근거를 들어 정중히 설명합니다.

에이전트 작업 흐름 이탈이 발생하면 아래 순서로 대응합니다.

1. 어떤 절차가 지켜지지 않았는지 확인합니다.
2. 기존 문서에 이미 해당 규칙이 있는지 확인합니다.
3. 규칙이 있다면 문서를 늘리지 않고, 해당 규칙의 위치·형태·트리거가 실패 원인인지 판단합니다.
4. 규칙이 없다면 어느 문서에 무엇을 추가해야 하는지 사용자에게 제안하고 승인을 받은 뒤 반영합니다.
5. Aeterna 기획 기준과 관련된 이탈이면 설계 변경인지 단순 위반인지 구분합니다.
6. 반영 후 관련 문서끼리 중복되거나 충돌하지 않는지 확인합니다.
7. 규칙 추가·변경·이동·삭제 결과를 `docs/RULE_ORIGINS.md`에 기록합니다.

## 이탈 대응 출력 양식

하네스 이탈을 스스로 인지했거나, 지적받은 이탈이 사실로 확인되면 반드시 아래 형식을 채워 출력한 뒤 대응을 진행합니다.

**[하네스 이탈 대응]**
- 지켜지지 않은 절차: (어느 문서의 어떤 규칙인지)
- 기존 규칙 존재 여부: 있음(문서명과 규칙) / 없음
- 실패 원인: (규칙 위치, 트리거, 양식 부재, 문서 충돌 등)
- 문서 반영안: (보강·형태 변경·이동·삭제·완화 또는 신규 추가 제안)
- Aeterna 기획 기준 영향: 있음(영향 내용) / 없음
- `RULE_ORIGINS` 기록안: (이 사례를 장부에 남길 한 줄)
- 세션 한정 수정만 안내하고 종료하지 않음

`문서 반영안`에 “다음부터 잘 지키겠다”와 같은 재준수 다짐만 적는 것은 인정하지 않습니다. 규칙이 명확한데도 실패했다면 왜 그 규칙이 실제 작업 시점에 작동하지 않았는지 함께 적습니다.

## 규칙 추가 판단

새 규칙이나 제약을 추가하기 전에는 아래 순서로 판단합니다.

1. 기존 문서 중 어느 문서가 이 규칙을 담당해야 하는지 확인합니다.
2. 기존 문서에 넣으면 역할이 섞이거나 문서가 비대해지는지 확인합니다.
3. 여러 문서에 걸친 운영 기준이면 독립 문서가 더 적합한지 확인합니다.
4. 새 컨텍스트가 반드시 알아야 하는 기준이면 `AGENTS.md` 또는 먼저 읽을 문서 목록에서 참조되게 합니다.
5. 규칙을 추가, 변경, 이동, 삭제할 때는 원인이 된 실패 사례나 결정 이유를 `docs/RULE_ORIGINS.md`에 함께 기록합니다.
6. 출처를 모르는 기존 규칙은 장부에 `기억 안 남`으로 표시하고 재검증 우선 대상으로 둡니다.
7. 문서 본문의 HTML 주석은 동기화나 유지보수에 실제로 필요한 경고에만 사용합니다.
